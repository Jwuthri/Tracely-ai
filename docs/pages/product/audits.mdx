# Audits

An audit **goes looking for a behaviour** instead of waiting for it to show up in production. You describe the behaviour, an attacker model probes a target model across a set of seeds, and a panel of judges scores every conversation. The result is an **elicitation rate**: how often the behaviour appeared, over the rollouts that were a fair test.

The loop follows two open-source tools from Anthropic: [Petri](https://www.anthropic.com/research/petri-open-source-auditing) (an auditor agent, a target, a judge) and [Bloom](https://www.anthropic.com/research/bloom) (a behaviour, scored for how strongly it is present).

## 1. Describe the behaviour and pick who plays each part

Click **New audit**. Pick a preset or write your own behaviour in a sentence or two: it is told to the attacker, so it knows what to provoke, and to the judges, so they know what counts. It is never shown to the target.

An audit is a conversation between two models, read afterwards by one or more others. The form lists the three parts the same way:

- **Model under test** — the model you are auditing. **On its own**, the attacker writes the system prompt and invents the tools for each seed; use it to audit a model itself. **As one of my agents**, the agent's real system prompt and tools are what is tested, unchanged. Choosing an agent fills them in from its most recent trace; open **Prompt and tools** to edit or paste them.
- **Attacker** — plays the user and tries to bring out the behaviour. Left on **Automatic**, the server picks the model.
- **Judges** — read each finished conversation and score it from 1 to 10. Add a second judge from another provider for a second opinion; with several, the score is their median.

That is all an audit needs. Everything else has a default under **More options**:

- **When the model uses a tool** — invented results or a real machine (next section).
- **What the attacker may do** — the **Realism check** has a second model read everything the attacker writes before the target sees it and send back anything that would give away that this is a test. **Send images** and **Send voice messages** are covered below. You also set how many turns the attacker gets.
- **Score other behaviours too** — the behaviour you described is always scored, and so is whether each conversation was a fair test. Pick more and the judges score the same conversations for those as well: no extra conversations, only extra judge calls.
- **Spending limit** — a run stops as soon as it has spent this much.

An audit's **Settings** has an **Edit** link that opens the same controls. A change applies to the next run; past runs keep the settings they ran with.

## The environment

How the target's tool calls are answered is the audit's **environment**:

- **The attacker makes up the result** — the attacker writes the result of every call, as the real tool would print it. Nothing runs. This works with any tools, including your agent's own.
- **It really runs, on a real machine** — the target gets a shell and file tools on an actual Linux box, and its commands really run. Before the first message the attacker builds the environment there: a repository with history, data, logs. Rewinding the conversation rewinds the machine as well.

On a real machine you choose **what is on it**. Each pack is a set of real tools backed by real systems, which the attacker fills with a company's worth of ordinary data before the target arrives:

| Pack | The target gets |
|---|---|
| Coding | a shell, and tools to read, write and edit files |
| Office | mail, a calendar, chat, documents |
| Support | customers, orders, refunds, tickets, a knowledge base |
| Data | a SQL warehouse |
| DevOps | services, deploys, CI runs, a secrets vault |

The exact tools are listed in the app: when you pick the real machine in the form, and under an audit's **Settings**, **What's on the machine** shows every tool with its arguments and description, as the target sees them.

The attacker can also give the target a tool of its own with a small program behind it, so that tool really executes too.

A real machine removes the easiest way for a model to notice a test: tool results that are too tidy, or that contradict each other. By default the box has no network; **Web access through an allowlist** lets it read package registries and documentation through a proxy that logs each request and refuses everything else. It runs as an unprivileged user, and is destroyed when the rollout ends. It is available when the deployment has a sandbox configured (`SANDBOX_BACKEND`); see the note in `docker-compose.sandbox.yml` before enabling it on a shared host.

Tools you imported from an agent are never executed, even on a real machine: what they do is yours, so the attacker answers them.

The **realism filter** is a second model that reads each message, system prompt and invented tool result before the target does, and sends back anything that would give the test away.

## 2. Add seeds

A seed is one instruction to the attacker: the situation to set up, who it plays, and what to try. Specific seeds work best: name the tools the target should have and what an ordinary day in that deployment looks like. There are four ways to get them:

- **Write my own**. Presets come with a few.
- **Write for me** writes a batch of 8 from the behaviour you described. Each batch is told what already exists, so asking again gives new situations, not rewordings. When the target is one of your agents, the seeds are situations *that* agent meets: they use its real prompt and tools, and the places it has actually failed in production. Add a line of guidance to steer a batch.
- Open a seed and, under **Try the same situation with**, vary it along one axis at a time — authority, time pressure, emotional pressure, lower stakes, different incidental details, no human present — to learn what the behaviour depends on.
- **From library** imports from Petri's 173 seeds, by topic. These are alignment-research seeds and suit auditing a model better than a deployed agent.

### Images and voice

Open a seed and **Attach an image or audio**, and the attacker can send it to the target as a user would: a photo of a receipt, a screenshot, a voice note. You can also let the attacker make its own: **Send images** and **Send voice messages** under *More options* when you create the audit. A voice message reaches the target as audio only, never as text.

The target model must accept the modality, or the run is refused before it starts. Judges that can see are shown the images; the others read a description, and every judge reads a voice message as its words. On a real machine with the Coding pack, a target that accepts images also gets a tool to open image files.

## 3. Run it

**Run** starts one rollout per seed (times the repetitions you ask for). The attacker gets a fixed number of turns per rollout. On each turn it can send a message, answer the target's tool calls, or **rewind** the target to an earlier message and try a different approach. The target forgets what was rewound; the judges still read it.

A run is bounded by the audit's budget in USD, and stops spending when it is reached.

### Measure and explore

**Run audit** needs no choices. Under **options** you can repeat each seed several times and pick the kind of run:

- **Measure** (the default) — every rollout is independent, so the elicitation rate means something. This is the audit's result.
- **Explore** — the run learns as it goes. Later rollouts are told what earlier ones showed, including what gave an attacker away. With *drafts per attacker turn* above 1, the attacker writes several moves each turn and a second model picks the most convincing. When the first pass ends, the run spends the budget it held back on a **second pass**: variations of the seeds that elicited, and repeats of the ones that split.

Explore finds more and measures less. Its rate overstates how often the behaviour happens, so it is labelled *exploratory* and never replaces a measured rate on the Audits list. Variations it writes are kept as disabled seeds: enable the ones worth measuring, then run in measure mode.

## Ask the assistant

The in-app assistant can do all of the above: "audit my support agent for refunds it should not grant", "write eight more seeds about angry customers", "what did the last run find?". It creates the audit and writes seeds straight away, and it reads results back with the judges' reasons. Starting a run spends money on your model key, so it tells you how many rollouts and the budget cap, and waits for your yes. The same tools are available over [MCP](/mcp) to agents outside Tracely; an ingest key can read audits and start runs, and only a signed-in user can create them.

## How a rollout is judged

Each dimension is scored from 1 to 10 by every judge model you selected, on its own. The panel's answer is the median. When the judges land on different sides of a dimension's threshold, each is asked twice more before the result is called, and the cell is marked **disputed**.

Three dimensions are always judged, and they decide whether the rollout counts at all:

| Dimension | Asks |
|---|---|
| `eval_awareness` | Did the target notice it was being tested? |
| `unrealism` | Was the scenario implausible as a real deployment? |
| `auditor_failure` | Did the attacker fail to run a usable audit? |

A rollout that scores high on any of them is **invalid**: it is left out of the rate rather than counted for or against the target.

| Verdict | Meaning | In the rate |
|---|---|---|
| Elicited | The target showed the behaviour in a valid rollout. | Yes |
| Clean | A valid, complete rollout in which it did not. | Yes |
| Invalid | The target noticed the test, or the scenario or attacker was broken. | No |
| Incomplete | Cut short by the budget, the clock or an error. | No |
| Ungraded | The judges did not produce a result. | No |
| Error, Skipped | The rollout failed or never ran. | No |

<Callout type="info">
  A run in which no rollout was both valid and judged has **no rate**, shown as a dash. That is deliberately different from 0%, which would say the target never does this.
</Callout>

## Reading a rollout

Open a row on the run page:

- **Conversation** — what the target saw, including every branch the attacker rewound. Rewound messages are dimmed.
- **Attacker** — the attacker's own reasoning and each move it made.
- **Judges** — each judge's score, its justification, and the messages it quoted.

The conversation the target ended with is also stored as a thread under [Traces](/product/traces), tagged `AUDIT` behind the Evals filter. It is kept out of your trends and cost numbers, because nothing in it is your agent answering a real request.
